# سرویس اینستاگرام Sepand Steel — آمادهٔ استقرار، خاموش

این پروژه از اسکلت اولیه به یک سرویس دریافت وب‌هوک با اعتبارسنجی، ثبت پایدار رویدادهای تکراری، گزارش‌های بدون متن پیام و آزمون‌های محلی تبدیل شده است. **هیچ استقرار، اتصال به Meta، تغییر تنظیمات، دریافت توکن یا ارسال پیامی انجام نشده است.** Make استفاده نمی‌شود.

حساب هدفِ اعلام‌شده `@sepandsteel`، صفحهٔ موردنظر `Mahdi.gorji` و برنامهٔ Meta موردنظر `directminion` هستند. این نام‌ها فقط زمینهٔ پروژه‌اند؛ مالکیت، شناسهٔ عددی، مجوزها، نوع ورود و وضعیت فعلی آن‌ها در این مرحله بررسی یا تغییر داده نشده است.

## دقیقاً چه چیزی آماده است؟

- دریافت در `/webhooks/instagram` با GET برای challenge و POST برای رویداد امضاشده.
- بررسی HMAC-SHA256 روی بایت‌های خام، مقایسهٔ زمان‌ثابت، رد JSON و UTF-8 نامعتبر، محدودیت بدنه، هدر، تعداد رویداد و زمان اتصال.
- محدودکردن دریافت به شناسه‌های عددی حساب اینستاگرام در allowlist محیطی؛ نام صفحه یا username جایگزین شناسه نیست.
- شناسایی دایرکت ورودی در `entry.messaging[].message.mid` و نظر در `entry.changes[]` با فیلد `comments` و `value.id`. read/delivery/postback، سایر فیلدها، echo، رویداد حذف‌شده و موارد مشخصاً متعلق به خود حساب نادیده گرفته می‌شوند. این فیلترها برای پاسخ‌گویی تأییدشده کافی فرض نشده‌اند.
- ذخیره فقط fingerprint کلیددار و زمان انقضا در SQLite؛ نه متن پیام، نه payload، نه شناسهٔ خام، نه token. هیچ طبقه‌بندی با کلمات کلیدی یا متن پاسخ موقت وجود ندارد.
- ثبت تراکنشی تمام رسیدهای یک درخواست پیش از پاسخ ۲۰۰؛ در خطای پایگاه داده، پاسخ ۵۰۳ با `Retry-After` داده می‌شود. درخواست تکراری دوباره ثبت نمی‌شود، حتی پس از restart.
- `/healthz` برای زنده‌بودن و `/readyz` برای دسترس‌پذیری پایگاه داده، با خروجی محدود و بدون تنظیمات محرمانه.
- اجرای non-root در Dockerfile، خاموشی پیش‌فرض، توقف کنترل‌شده با SIGTERM/SIGINT و لاگ ساخت‌یافته با شمارنده و کد ثابت.

**این نسخه فقط receive-only است.** هیچ adapter ارسال، فراخوانی Graph API، job پاسخ‌گویی یا صف ارسال ندارد. «ثبت رسید» به معنی پاسخ‌دادن یا پردازش محتوای پیام نیست؛ خروجی همواره `processed: false` و `outbound: disabled` است. این نسخه برای استقرار گیرنده آماده است، نه برای راه‌اندازی خودکار پاسخ‌های واقعی.

## دو قفل مستقل

`ENABLE_WEBHOOK_RECEIVER=false` پیش‌فرض است. `npm start` بدون فعال‌سازی صریح و تنظیمات معتبر، با خطا خاتمه می‌یابد و هیچ پورتی باز نمی‌کند.

`ENABLE_OUTBOUND_REPLIES=false` قفل خروجی است. مقدار `true` یا مقدار نامعتبر باعث رد startup می‌شود، نه فعال‌شدن ارسال. حتی با روشن‌بودن گیرنده هیچ مسیری برای ارسال وجود ندارد. پیاده‌سازی ارسال فقط پس از بررسی و تأیید جداگانهٔ رفتار دقیق ممکن است.

هیچ `ACCESS_TOKEN` یا تنظیم توکن دسترسی در این نسخه وجود ندارد. توکن تهیه‌شدهٔ مالک برای این کار لازم نیست و نباید به این پروژه اضافه شود. App Secret برای بررسی امضا با access token فرق دارد.

## آزمون امن محلی

نیازمند Node.js نسخهٔ ۲۴ است؛ از `node:sqlite` داخلی استفاده می‌شود و وابستگی npm خارجی ندارد. API داخلی SQLite در این نسخه از Node ممکن است هشدار Experimental بدهد؛ فقط همان هشدار در دستور اجرا مخفی شده است.

```bash
cd /workspace/sepandsteel-instagram-draft
npm test
npm run check
```

آزمون‌ها فقط با دادهٔ ساختگی روی `127.0.0.1` اجرا می‌شوند و پایگاه دادهٔ موقتشان پاک می‌شود. هیچ token واقعی، تماس Meta یا پیام واقعی لازم ندارند. برای آزمون‌ها secret واقعی تنظیم نکنید.

## تنظیمات برای استقرار آینده، فقط پس از تأیید

فایل `.env.example` صرفاً الگوست؛ برنامه آن را خودکار بارگذاری نمی‌کند. اسرار باید از secret manager میزبان به محیط فرآیند تزریق شوند، نه از فایل commitشده یا Docker image.

| متغیر | کاربرد |
| --- | --- |
| `ENABLE_WEBHOOK_RECEIVER` | پیش‌فرض `false`؛ روشن‌کردن فقط با مجوز جداگانه |
| `ENABLE_OUTBOUND_REPLIES` | باید `false` بماند؛ روشن‌کردن در این نسخه ممنوع و غیرعملیاتی است |
| `META_APP_SECRET` | secret برنامه برای اعتبارسنجی امضا |
| `META_VERIFY_TOKEN` | secret مستقل و تصادفی برای handshake وب‌هوک |
| `DEDUPE_HMAC_KEY` | secret مستقل و ثابت برای ناشناس‌سازی شناسه‌ها |
| `INSTAGRAM_ACCOUNT_IDS` | شناسهٔ عددی حرفه‌ایِ تأییدشده، جداشده با کاما |
| `HOST` / `PORT` | پیش‌فرض محلی `127.0.0.1:3000`؛ داخل image، HOST برابر `0.0.0.0` است |
| `DEDUPE_DB_PATH` | مسیر مطلق روی دیسک پایدار؛ الگو `/data/events.sqlite` |
| `DEDUPE_RETENTION_SECONDS` | پیش‌فرض ۶۰۴۸۰۰ ثانیه، یعنی ۷ روز؛ بازهٔ مجاز ۱ تا ۹۰ روز |
| `DEDUPE_MAX_RECORDS` | پیش‌فرض ۱۰۰٬۰۰۰ رسید؛ پرشدن باعث ۵۰۳ می‌شود |
| `MAX_BODY_BYTES` | پیش‌فرض ۱ MiB، سقف تنظیم‌پذیر ۴ MiB |
| `MAX_EVENTS_PER_REQUEST` | پیش‌فرض ۱۰۰۰ رویداد؛ تعداد entryها نیز جداگانه به همین سقف محدود است |

سه secret باید متفاوت، غیرنمونه‌ای و حداقل ۳۲ بایت باشند. verify-token و کلید dedup باید تصادفی تولید شوند؛ secret واقعی Meta همان مقدار معتبر برنامه است. هنگام تعویض کلید dedup، رویدادهای قبلی ممکن است دوباره جدید تلقی شوند؛ تعویض آن نیازمند برنامهٔ مشخص است.

پوشهٔ پایگاه داده باید متعلق به کاربر فرآیند باشد و برای سایر کاربران قابل نوشتن نباشد. فایل DB با مجوز `0600` و پوشهٔ جدید با `0700` ساخته می‌شود. مسیر و تمام پوشه‌های بالادستی باید روی volume قابل اعتماد باشند، نه مسیر قابل تعویض توسط کاربر دیگر؛ این کنترل‌ها در برابر کاربر مخربِ هم‌هویت یا مدیر سیستم محافظت نمی‌کنند.

## بستهٔ استقرار

Dockerfile آماده شده اما در این مرحله build، run یا deploy نشده است. این دستورات صرفاً راهنمای اقدام آینده‌اند:

```bash
# فقط پس از تأیید مالک؛ این دستورات در این مرحله اجرا نشده‌اند.
docker build -t sepandsteel-instagram:1.0.0 .
# مقداردهی اسرار، volume، TLS و روشن‌کردن گیرنده نیازمند بررسی جداگانه است.
```

برای استقرار واقعی: یک replica پشت reverse proxy دارای HTTPS معتبر، شبکهٔ داخلی برای پورت برنامه، volume پایدار و backup حفاظت‌شده لازم است. image برای کاربر `node` است؛ مالکیت mount باید با UID کاربر image سازگار باشد. filesystem برنامه را تا حد امکان read-only و فقط volume داده را قابل نوشتن نگه دارید. SQLite روی دیسک محلی قابل اعتماد استفاده شود، نه فایل مشترک NFS یا چند replica با volumeهای جدا. image و نسخهٔ پایه در خط استقرار نهایی باید اسکن و ترجیحاً با digest ثابت شوند.

روی reverse proxy و سرویس میزبانی، rate limit، سقف اندازه/زمان درخواست و محدودیت concurrency بگذارید. access log نباید query string وب‌هوک، هدر امضا، secret یا بدنهٔ پیام را ثبت کند؛ verify-token در درخواست GET قرار می‌گیرد. logهای برنامه فقط event ثابت و شمارنده‌اند. مانیتورینگ باید خطای signature، خطای storage، ۵۰۳، فضای دیسک و restart را پوشش دهد.

## محدودیت‌هایی که نباید با تضمین اشتباه شوند

HMAC صحت و انتساب بدنه را بررسی می‌کند، نه تازگی آن را. Meta در این قرارداد timestamp امضای جداگانه‌ای به این سرویس نمی‌دهد؛ fingerprint فقط در بازهٔ نگهداری جلوی ثبت مجدد را می‌گیرد. رسیدهای منقضی هنگام POST بعدی پاک می‌شوند؛ حذف فیزیکی امن از دیسک یا backup تضمین نمی‌شود. برنامهٔ نگهداری و backup باید جداگانه تأیید شود.

fingerprint از حساب + نوع رویداد + ID ساخته می‌شود. تغییر متن همان comment با ID ثابت، یک رویداد تازه محسوب نمی‌شود. حذف و ویرایش نظر در این نسخه گردش کار مستقلی ندارند. فیلد ناشناخته نادیده گرفته می‌شود؛ قرارداد رخداد واقعی و نمونه‌های به‌روز Meta باید پیش از اتصال نهایی تأیید شوند.

این dedup فقط برای **رسید دریافت** است، نه تضمین exactly-once برای پیام خروجی. وقتی ارسال در آینده تأیید شود، به outbox پایدار، سیاست retry/ابهام ارسال، قواعد زمان مجاز پیام، کنترل حلقه و بررسی خطا نیاز خواهد داشت. رسیدهای این نسخه نباید بعداً خودکار به صف پاسخ تبدیل شوند؛ پاسخ به رویدادهای قدیمی نیاز به تأیید جداگانه دارد.

## چه چیزهایی هنوز نیازمند تأیید مالک است؟

۱. **رفتار دقیق پاسخ‌ها:** کانال‌ها، رویدادهای مجاز، کلمات کلیدی نهایی، متن هر پاسخ، عمومی یا خصوصی بودن، موارد بدون پاسخ، سقف تعداد، پاسخ تکراری، ساعات، ارجاع به انسان، اطلاعات قیمت/موجودی و شیوهٔ توقف. هیچ متن یا قاعدهٔ پیشنهادی قبلی قطعی فرض نشده است.

۲. **استقرار و دریافت واقعی:** میزبان، دامنه، هزینه، TLS، شناسهٔ عددی حساب، دورهٔ نگهداری، مسئول دسترسی/backup و اجازهٔ روشن‌کردن گیرنده. این تأیید به‌تنهایی مجوز پاسخ‌گویی نیست.

۳. **اتصال Meta:** تأیید حساب/صفحه/برنامه، مسیر درست Instagram Login یا Facebook Login، نوع توکن، نسخهٔ API، مجوزها و نیازهای review/live طبق مستندات رسمیِ زمان اتصال؛ سپس تأیید ثبت callback و subscriptionهای دقیق. وضعیت فعلی Meta در این کار بررسی نشده است.

۴. **ارسال واقعی:** بازبینی پیاده‌سازی جدید خروجی و outbox، آزمون محدود موردتأیید مالک و اجازهٔ صریح جداگانه برای فعال‌کردن ارسال. تا آن زمان نه توکن دسترسی درخواست یا ذخیره شود و نه کلید خروجی روشن شود.

## فایل‌های اصلی

`server.js`: HTTP، اعتبارسنجی، استخراج شناسه‌ها و پاسخ receive-only؛ `config.js`: تنظیمات محیطی و قفل‌ها؛ `store.js`: رسیدهای SQLite؛ `test.js`: آزمون‌های مصنوعی؛ `Dockerfile` و `.dockerignore`: بستهٔ ساخت بدون secrets؛ `.gitignore`: حذف اسرار و داده‌ها از کنترل نسخه.
